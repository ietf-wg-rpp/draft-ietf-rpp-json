# Agents.md — JSON for RESTful Provisioning Protocol (RPP)

## Project Overview

This repository contains the IETF Internet-Draft for **JSON for Restful
Provisioning Protocol (RPP)** (`draft-wullink-rpp-json`, individual submission to
the Network Working Group). The document defines how RPP data objects — as defined
in `[@!I-D.ietf-rpp-data-objects]` — are represented in JSON `[@!RFC8259]`,
including normative JSON Schema definitions (draft 2020-12) and worked examples for
domain name, contact, and host data objects. It is authored in Markdown for mmark
and compiled to XML (xml2rfc v3), HTML, PDF, and TXT.

## Authoring Toolchain — mmark / Markdown

- Source format: Markdown for [mmark](https://mmark.miek.nl/) (CommonMark +
  extensions for RFCXML).
- Build (via `src/Makefile`, which writes outputs into `docs/`):
  - `mmark draft-wullink-rpp-json.md > ../docs/draft-wullink-rpp-json.xml` (`make xml`)
  - `xml2rfc --text/--html/--pdf --v3 ../docs/...xml` (`make txt|html|pdf`)
  - `make all` builds txt, html, pdf, and the no-pagination `.clean.txt`.
- mmark uses a TOML title block (between `%%%` fences) for document metadata
  (`title`, `ipr`, `area`, `workgroup`, `submissiontype`, `[seriesInfo]`,
  `[[author]]`, …). The draft revision number lives in `[seriesInfo].value`
  (currently `draft-wullink-rpp-json-02`).
- mmark-specific syntax to know: block attributes `{#anchor}` for cross-reference
  targets, `[@!RFCxxxx]` (normative) / `[@RFCxxxx]` (informative) /
  `[@?RFCxxxx]` citations, `{type="..."}` on lists, and fenced
  `sourcecode`/`artwork` blocks. JSON Schema and example blocks are plain
  triple-backtick fences.

## Conventions

### Literals

- House style: render literal tokens (JSON keys, type names, enum/`@type` values,
  parameter values) as inline code with the **double-quotes inside the backticks** —
  e.g. `` `"domainName"` ``, `` `@type` ``. Apply consistently to every literal.
- JSON Schema and example code use plain triple-backtick fenced blocks. Keep them
  valid JSON; the consistency checker will fail otherwise.

### Cross-references and anchors

- mmark anchor: `{#my-anchor}` trailing a heading/block.
- Reference: `[](#my-anchor)` or `(#my-anchor)`.
- Keep anchors stable: other sections and external readers may link to them. Never
  silently rename or drop an anchor during a restructure.

### Citations / references

- `[@!RFCxxxx]` for **normative**, `[@RFCxxxx]` for **informative**, `[@?RFCxxxx]`
  for references mmark resolves leniently. mmark auto-fetches reference XML from the
  IETF bibliography.
- Classify each new reference as Normative or Informative deliberately — this
  affects the published RFC. Normative refs already in use include
  `[@!RFC8259]`, `[@!RFC2119]`, `[@!RFC9553]`, `[@!I-D.ietf-rpp-data-objects]`,
  `[@!I-D.wullink-rpp-core]`.

### RFC 2119 / 8174 requirement keywords (markup)

Write the keywords in plain all-caps (e.g. `MUST`, `SHOULD`, `MAY`). The normative
*meaning* is covered under **Writing Style → Normative language** below.

## Writing Style

IETF specifications have a distinct, conservative house style. Apply it to all
prose you add or edit. The goal is a document that an independent implementer can
turn into interoperable code without guessing.

### Normative language (RFC 2119 / BCP 14)

- Use **MUST / MUST NOT / REQUIRED / SHALL / SHALL NOT / SHOULD / SHOULD NOT /
  RECOMMENDED / NOT RECOMMENDED / MAY / OPTIONAL** only in their RFC 2119 sense,
  and **only in all-caps**. In lowercase they are ordinary English words with no
  normative force.
- Every normative keyword places a requirement on a **specific actor** (RPP client,
  RPP server, generator, parser) for a **specific, testable behaviour**.
- Don't stack keywords ("MUST … REQUIRED to …"); pick one. Don't use a keyword
  where plain present tense states a fact ("the field *contains* a timestamp").
- Reserve **SHOULD** for genuine implementer discretion and say what to weigh; if
  there is no legitimate reason to deviate, it is a **MUST**.
- State **error handling and behaviour on receipt of malformed/unexpected input**
  explicitly, including what a receiver does with values it doesn't recognise
  (forward-compatibility / "must-ignore" rules).

Per the IESG Statement on Clarifying the Use of BCP 14 Key Words
(<https://www.ietf.org/about/groups/iesg/statements/clarifying-use-bcp14/>):

- **Use the key words sparingly** — only where required for interoperability or to
  limit behaviour with potential for harm. They are not for emphasis. A normative
  statement does not need a key word; plain declarative prose is equally normative.
- **Justify every SHOULD / RECOMMENDED**, stating what a conformant implementation
  must weigh before deviating.
- **Do NOT use BCP 14 key words** in the Abstract, IANA Considerations, examples,
  figures/captions, or appendices. This matters here: the draft is example-heavy —
  keep the JSON examples and their surrounding captions free of normative keywords.

### Specify, don't describe

- Write **declarative, present-tense** requirements, not narrative or marketing
  prose. Name the conformance target (client, server, generator, parser).
- Specify **both sides**: what a generator produces *and* what a parser must accept.
- Give the encoding precisely: character encoding (UTF-8), case sensitivity (JSON is
  case-sensitive — already stated in *Conventions Used in This Document*), defaults,
  ranges, and units. Prefer explicit enumerations and ranges over vague adjectives.
- Keep JSON Schema definitions and the surrounding prose in sync — the schema is the
  formal syntax for this document.
- Keep the prose introducing a JSON Schema object to the bare minimum needed to
  understand its JSON representation (typically one sentence). Do not repeat
  descriptions or rules already defined in `[@!I-D.ietf-rpp-data-objects]`.
- Always keep the block "The following constraints cannot be expressed in JSON
  Schema and MUST be enforced by implementations:" with its bullets where such
  constraints exist.
- Record standing preferences like these in this file, not in Agent's memory.

### Terminology discipline

- Define each term **once** in the Terminology section, then use it consistently —
  no synonyms for a defined term.
- Reuse terminology from existing RFCs (RFC 8259 for JSON, RFC 9553 for JSContact,
  RFC 1035 for DNS, RFC 5730 family for EPP) rather than reinventing it; cite the
  source and don't redefine borrowed terms.
- **Expand every acronym on first use** (e.g. "RESTful Provisioning Protocol (RPP)",
  "JavaScript Object Notation (JSON)"); RFC 7322 exempts a short list of well-known
  abbreviations.

### Structure and cross-references

- Lead each major section with a one-sentence statement of its purpose.
- Keep rationale/history in non-normative places; mark examples as illustrative,
  not authoritative — they must stay consistent with the normative schema and rules.
- Cross-reference with anchors instead of duplicating a requirement in two places.

### Document structure and required sections (RFC 7322)

Current body order: Introduction → Terminology → Conventions Used in This Document
→ JSON Representation Rules → JSON Schema Definitions → Examples → IANA
Considerations → Internationalization Considerations → Security Considerations →
Acknowledgments → Change History. When adding sections, preserve RFC 7322 ordering.

- **Abstract** — standalone; **MUST NOT contain citations or references** in the
  rendered RFC sense, and must not just duplicate the Introduction.
- **IANA Considerations** — required; list every registry action precisely or state
  "This document has no IANA actions." Don't leave it as a bare TODO at submission.
- **Internationalization Considerations** — present; keep it substantive given the
  draft carries human-readable contact data (JSContact).
- **Security Considerations** — **required and substantive**, not a placeholder;
  give threat model, what is and isn't protected, residual risks (BCP 72 / RFC 3552).
- **Privacy Considerations** — the draft carries personal data (contacts via
  JSContact). If privacy is not addressed in its own section, consider adding one
  per RFC 6973, or state explicitly where/why it is covered elsewhere.
- **References** — split Normative / Informative, ordered by tag, no intro prose.

### Tone and mechanics

- Neutral and precise; avoid hype and hedging ("simply", "just", "obviously").
- Distinguish "i.e." (that is) from "e.g." (for example).
- One requirement per sentence where practical.
- Be **consistent** in spelling (the draft uses British spellings, e.g.
  "Authorisation", "Organisation", "standardised" — match them). Serial (Oxford)
  comma is the IETF default.
- Use **title case** for the document title and section titles.
- **Use reserved example domains/addresses** (RFC 2606 / BCP 32: `example.com`,
  `example.net`, `.example`; RFC 5737 / RFC 3849 IP ranges) in all examples — never
  real domains or addresses.
- Wrap bare URIs in angle brackets (`<https://example.com/>`).
- Run **idnits** (or the datatracker submission checks) before submitting.

### Writing Change History Entries

Each substantive edit gets a bullet under the current draft revision's `=== Change from … to …` heading (create the heading for the new revision if it does not yet exist).

Keep entries **terse**: state the action and point to the affected section by cross-reference, then stop. Do **not** append a summary of what the section now says or why the change was made — the cross-referenced section is the source of truth for that detail.

- Pattern: `<Verb> <<anchor,format=title>> to/in <<section-anchor,format=title>>.` (e.g. `Added`, `Clarified`, `Removed`, `Restructured`).
- Reference sections with `<<anchor,format=title>>`, not by literal title text, wherever an anchor exists.
- One bullet per logical change. Do not fold rationale, threat descriptions, or normative detail into the bullet.
- Good: `- Clarified handling of multiple `"_domainconnect"` TXT records in <<dns-provider-discovery,format=title>>.`
- Avoid: `- Clarified handling of multiple `"_domainconnect"` TXT records in <<dns-provider-discovery,format=title>>: invalid records are rejected, at least one valid record is processed, and the Service Provider MAY iterate…` (trailing explanation belongs in the section, not the history).

## Edit Workflow

**CRITICAL**: All edits to the source document MUST follow this workflow. No
exceptions.

**CRITICAL — Never restore manually-removed content**: If the user has edited or
removed content directly in the source file, NEVER re-add, restore, or reintroduce
that content. The user's manual edits are authoritative. Before applying any edit,
re-read the region if unsure so an `old_string`/`new_string` block does not silently

**CRITICAL — Bulk structural edits MUST be scripted**: Any change that repeats the
same structural transformation across many places (e.g. re-quoting every literal,
rewrapping every list entry, transforming many JSON blocks) MUST be done with a
throwaway script (`.work-*.py` or similar), NOT a series of hand-written `Edit`
calls. The script:

- **Transforms structure only, never rewrites prose.** Re-emit existing
  cells/lines verbatim; only markup may change.
- **Is verified before trusting it.** Snapshot first (`cp src/draft-wullink-rpp-json.md /tmp/before`),
  run, then diff: confirm document prefix and tail are byte-identical and only the
  intended structural tokens changed. Preserve all anchors.
- **Respects manual edits.** Drive off the current file state; skip already-converted
  items.
- **Is deleted afterward** along with any `/tmp` snapshot. Do not commit `.work-*.py`.
- After bulk edits to JSON, run `.scripts/check_json_consistency.py`.

Still follow the propose-and-approve steps below before running the script on the

## Pre-Release Review

Run this process **only when the user asks for a final pre-release review**
(e.g. before submitting a new revision to the datatracker). It is a whole-document
pass, so it is the one case where every section is read — still in
`offset`/`limit` chunks guided by the Document Index, never in a single read.

### Process

1. **Prepare.** Run `./update-index.sh` and read `.agent-index.md`. Run the IANA
   consistency script (`cd src && python3 ../.scripts/check_iana_consistency.py`)
   as a baseline and note its result. Check `git diff` for uncommitted manual
   edits (e.g. to the title block) — they are the user's and are authoritative.
2. **Read and collect (read-only).** Read the title block and Changes History,
   then the whole body, IANA Considerations, and backmatter in chunks of a few
   hundred lines. Note findings as you read; apply nothing.
3. **Mechanical sweeps.** Complement the reading with greps for things that are
   easy to miss by eye: trailing whitespace, non-ASCII characters, semicolons in
   prose, mixed-case BCP 14 keywords (`MUST not`, `Must`, `MAY not`), citations
   without `@` (`[RFCxxxx]`), cited references vs references defined in the
   backmatter, `(#anchor)` targets without a matching `{#anchor}`, US spellings,
   `TODO`/`TBD`/`TBC` notes and HTML comments, and first use of acronyms.
4. **Cross-check what the script does not.** The IANA script compares elements
   and operations, but also verify by hand: `Extends` values, operation
   identifiers present on every IANA operation, and element descriptions whose
   meaning (not only wording) differs between normative text and IANA.
5. **Number the findings.** Use one ID per issue (split grouped findings so each
   can be approved individually):
   * `Mxx` — Check 1 (header metadata).
   * `Hxx` — Check 2 (Changes History).
   * `Sxx` — Check 3 (spelling and UK/US consistency).
   * `Cxx` — Check 4 (whole-document consistency), grouped under subheadings
     (substantive defects, citations and references, BCP 14, open items and
     placeholders, style and mechanics), most severe first.
6. **Record the to-do list.** Write the findings to `.work/review_YYYYMMDD.md`
   (date of the review) as a checklist: one line per ID with line number(s),
   current text, and proposed fix. Note at the top that line numbers refer to
   the file state at review time, and record the IANA script baseline.
   Legend: `[ ]` open, `[x]` applied, `[-]` rejected, `[>]` deferred; mark
   approvals inline as `(approved)`.
7. **Present.** Show the findings to the user grouped by the four checks, with
   the same IDs. Flag findings that rename wire identifiers (element or
   operation identifiers, IANA entries) as needing an explicit decision.
8. **Apply on approval only.** Apply nothing until the user approves specific
   IDs or ranges (Edit Workflow, Steps 1–2). Repeated mechanical fixes (e.g. the
   same spelling change in many places, trailing whitespace) MUST be applied
   with a verified throwaway script, per the bulk-edit rule above. Substantive
   findings get exact proposed wording first.
9. **Keep the to-do file current.** After every approval, application,
   rejection, or deferral, update the item's state in
   `.work/review_YYYYMMDD.md`. After applying edits, run `./update-index.sh`,
   re-run the IANA script, and add Changes History entries where the edit is
   not itself a Changes History fix.

In the TOML title block:

- `date` MUST be today's date (`YYYY-MM-DD`), unless the user has set a planned

- `[seriesInfo] value` MUST be the exact name of the revision being released

- Check the Abstract: no citations, no BCP 14 key words, and a scope that
  matches the objects the document actually defines (same for the

### Check 2 — Changes History Consolidation

Review **only the subsection for the revision being released**. Look for entries
that:

- describe the same change made in several iterations (e.g. "Added X", later
  "Fixed X", later "Renamed X") — merge them into one entry describing the net
  result;
- touch the same area/section or the same issue number and can be expressed as
  one entry;
- describe a change that was later reverted within the same revision — propose
  removing both;
- are duplicates or near-duplicates.

Also check each entry against the **Changes History** rules above (lowercase
bullet text, `#NN` issue references, concise, WHAT not WHY, ASCII only).
Propose each merge as "entries A + B → new entry"; never silently drop an
entry. Do not touch older revisions' subsections.

### Check 3 — Full Spell Check and UK/US Consistency

Spell-check the entire document (prose, headings, table cells, figure captions,
and Changes History). Spelling policy:

- **Prose is UK English** (e.g. "behaviour", "authorisation", "organisation",
  "standardise", "recognise", "licence" (noun), "catalogue", "centre").
- **Protocol elements and literals stay exactly as defined** — never "correct"
  them: element, object, and operation identifiers, status values, URNs,
  registry field names, and anything inside backticks or fenced code blocks.
- **Titles and quoted terms of external documents** keep their original
  spelling: RFC and reference titles, organisation names in reference entries,
  and established external terms such as "Internationalized Domain Names" or
  "Unicode Normalization Form C".
- When prose refers to a concept that is also a literal, the prose word is UK
  and the literal is unchanged.

Report typos, grammar slips, UK/US inconsistencies, and inconsistent
hyphenation/capitalisation of recurring terms (e.g. "nameserver" vs
"name server", "lowercase" vs "lower case", "offline review" vs
"offline-review", "Uniform Interface" vs "Uniform interface", constraint
placeholders `(None)` vs `None` vs `-`, title case in headings). A tool such as
`aspell --lang=en_GB` or `hunspell -d en_GB` can be used to generate candidates
if available, but every candidate MUST be checked against the literal/quotation
exceptions above before it is proposed.

### Check 4 — Whole-Document Consistency Scan

Scan the full document for inconsistencies, including:

- **Object model:** stray or duplicated attribute bullets; elements referenced
  in prose (operations, constraints, examples) that no longer exist; content
  left over from earlier restructurings that contradicts the Changes History;
  `Extends`, identifiers, cardinality, or meaning differing between normative
  definitions and IANA tables; inconsistent operation identifiers across
  similar objects; the same requirement stated in two places.
- **Status models:** status values, exclusions, transition diagrams, state
  descriptions, and the corresponding IANA registries agree, and equivalent
  rules are stated consistently across objects.
- **Terminology:** defined terms (Conventions and Terminology) used
  consistently, without synonyms (e.g. "Data Object" vs "resource object") or
  EPP-only wording where RPP terms exist; acronyms expanded on first use.
- **Cross-references and citations:** broken or dangling `(#anchor)`
  references; references written without `@` (not rendered as citations);
  cited documents missing from References and defined references never cited;
  normative/informative classification that looks wrong (e.g. an informative
  reference that a MUST depends on); figure/table captions and anchors.
- **BCP 14:** mixed-case or non-keyword forms (`MUST not`, `MAY not`, `Must`);
  key words used as plain adjectives ("OPTIONAL elements"); key words in the
  Abstract, IANA Considerations, examples, or appendices.
- **Open items:** leftover `TODO`, `TBD`, `TBC` editor notes (including ones
  made stale by later changes), commented-out text, empty sections, IANA
  placeholders other than `TBDn`, and missing required sections (Security
  Considerations, Privacy Considerations where personal data is handled).
- **Mechanics:** semicolons in prose, non-ASCII characters, trailing
  whitespace, double spaces, missing blank lines before lists, example
  domains not using reserved names.

Report findings only; do not restructure or rewrite prose beyond the minimal fix
for each finding.
