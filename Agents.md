# CLAUDE.md — JSON for RESTful Provisioning Protocol (RPP)

## Project Overview

This repository contains the IETF Internet-Draft for **JSON for Restful
Provisioning Protocol (RPP)** (`draft-wullink-rpp-json`, individual submission to
the Network Working Group). The document defines how RPP data objects — as defined
in `[@!I-D.ietf-rpp-data-objects]` — are represented in JSON `[@!RFC8259]`,
including normative JSON Schema definitions (draft 2020-12) and worked examples for
domain name, contact, and host data objects. It is authored in Markdown for mmark
and compiled to XML (xml2rfc v3), HTML, PDF, and TXT.

## Authoring Toolchain — mmark / Markdown

- Source format: Markdown for [mmark](https://mmark.miek.nl/) (CommonMark +
  extensions for RFCXML).
- Build (via `src/Makefile`, which writes outputs into `docs/`):
  - `mmark draft-wullink-rpp-json.md > ../docs/draft-wullink-rpp-json.xml` (`make xml`)
  - `xml2rfc --text/--html/--pdf --v3 ../docs/...xml` (`make txt|html|pdf`)
  - `make all` builds txt, html, pdf, and the no-pagination `.clean.txt`.
- mmark uses a TOML title block (between `%%%` fences) for document metadata
  (`title`, `ipr`, `area`, `workgroup`, `submissiontype`, `[seriesInfo]`,
  `[[author]]`, …). The draft revision number lives in `[seriesInfo].value`
  (currently `draft-wullink-rpp-json-02`).
- mmark-specific syntax to know: block attributes `{#anchor}` for cross-reference
  targets, `[@!RFCxxxx]` (normative) / `[@RFCxxxx]` (informative) /
  `[@?RFCxxxx]` citations, `{type="..."}` on lists, and fenced
  `sourcecode`/`artwork` blocks. JSON Schema and example blocks are plain
  triple-backtick fences.

## Conventions

### Literals

- House style: render literal tokens (JSON keys, type names, enum/`@type` values,
  parameter values) as inline code with the **double-quotes inside the backticks** —
  e.g. `` `"domainName"` ``, `` `@type` ``. Apply consistently to every literal.
- JSON Schema and example code use plain triple-backtick fenced blocks. Keep them
  valid JSON; the consistency checker will fail otherwise.

### Cross-references and anchors

- mmark anchor: `{#my-anchor}` trailing a heading/block.
- Reference: `[](#my-anchor)` or `(#my-anchor)`.
- Keep anchors stable: other sections and external readers may link to them. Never
  silently rename or drop an anchor during a restructure.

### Citations / references

- `[@!RFCxxxx]` for **normative**, `[@RFCxxxx]` for **informative**, `[@?RFCxxxx]`
  for references mmark resolves leniently. mmark auto-fetches reference XML from the
  IETF bibliography.
- Classify each new reference as Normative or Informative deliberately — this
  affects the published RFC. Normative refs already in use include

## Writing Style

IETF specifications have a distinct, conservative house style. Apply it to all
prose you add or edit. The goal is a document that an independent implementer can
turn into interoperable code without guessing.

### Normative language (RFC 2119 / BCP 14)

- Use **MUST / MUST NOT / REQUIRED / SHALL / SHALL NOT / SHOULD / SHOULD NOT /
  RECOMMENDED / NOT RECOMMENDED / MAY / OPTIONAL** only in their RFC 2119 sense,
  and **only in all-caps**. In lowercase they are ordinary English words with no
  normative force.
- Every normative keyword places a requirement on a **specific actor** (RPP client,
  RPP server, generator, parser) for a **specific, testable behaviour**.
- Don't stack keywords ("MUST … REQUIRED to …"); pick one. Don't use a keyword
  where plain present tense states a fact ("the field *contains* a timestamp").
- Reserve **SHOULD** for genuine implementer discretion and say what to weigh; if
  there is no legitimate reason to deviate, it is a **MUST**.
- State **error handling and behaviour on receipt of malformed/unexpected input**
  explicitly, including what a receiver does with values it doesn't recognise
  (forward-compatibility / "must-ignore" rules).

Per the IESG Statement on Clarifying the Use of BCP 14 Key Words
(<https://www.ietf.org/about/groups/iesg/statements/clarifying-use-bcp14/>):

- **Use the key words sparingly** — only where required for interoperability or to
  limit behaviour with potential for harm. They are not for emphasis. A normative
  statement does not need a key word; plain declarative prose is equally normative.
- **Justify every SHOULD / RECOMMENDED**, stating what a conformant implementation
  must weigh before deviating.
- **Do NOT use BCP 14 key words** in the Abstract, IANA Considerations, examples,
  figures/captions, or appendices. This matters here: the draft is example-heavy —
  keep the JSON examples and their surrounding captions free of normative keywords.

### Specify, don't describe

- Write **declarative, present-tense** requirements, not narrative or marketing
  prose. Name the conformance target (client, server, generator, parser).
- Specify **both sides**: what a generator produces *and* what a parser must accept.
- Give the encoding precisely: character encoding (UTF-8), case sensitivity (JSON is
  case-sensitive — already stated in *Conventions Used in This Document*), defaults,
  ranges, and units. Prefer explicit enumerations and ranges over vague adjectives.
- Keep JSON Schema definitions and the surrounding prose in sync — the schema is the
  formal syntax for this document.

### Terminology discipline

- Define each term **once** in the Terminology section, then use it consistently —
  no synonyms for a defined term.
- Reuse terminology from existing RFCs (RFC 8259 for JSON, RFC 9553 for JSContact,
  RFC 1035 for DNS, RFC 5730 family for EPP) rather than reinventing it; cite the
  source and don't redefine borrowed terms.
- **Expand every acronym on first use** (e.g. "RESTful Provisioning Protocol (RPP)",
  "JavaScript Object Notation (JSON)"); RFC 7322 exempts a short list of well-known
  abbreviations.

### Structure and cross-references

- Lead each major section with a one-sentence statement of its purpose.
- Keep rationale/history in non-normative places; mark examples as illustrative,
  not authoritative — they must stay consistent with the normative schema and rules.
- Cross-reference with anchors instead of duplicating a requirement in two places.

### Document structure and required sections (RFC 7322)

Current body order: Introduction → Terminology → Conventions Used in This Document
→ JSON Representation Rules → JSON Schema Definitions → Examples → IANA
Considerations → Internationalization Considerations → Security Considerations →
Acknowledgments → Change History. When adding sections, preserve RFC 7322 ordering.

- **Abstract** — standalone; **MUST NOT contain citations or references** in the
  rendered RFC sense, and must not just duplicate the Introduction.
- **IANA Considerations** — required; list every registry action precisely or state
  "This document has no IANA actions." Don't leave it as a bare TODO at submission.
- **Internationalization Considerations** — present; keep it substantive given the
  draft carries human-readable contact data (JSContact).
- **Security Considerations** — **required and substantive**, not a placeholder;
  give threat model, what is and isn't protected, residual risks (BCP 72 / RFC 3552).
- **Privacy Considerations** — the draft carries personal data (contacts via
  JSContact). If privacy is not addressed in its own section, consider adding one
  per RFC 6973, or state explicitly where/why it is covered elsewhere.
- **References** — split Normative / Informative, ordered by tag, no intro prose.

### Tone and mechanics

- Neutral and precise; avoid hype and hedging ("simply", "just", "obviously").
- Distinguish "i.e." (that is) from "e.g." (for example).
- One requirement per sentence where practical.
- Be **consistent** in spelling (the draft uses British spellings, e.g.
  "Authorisation", "Organisation", "standardised" — match them). Serial (Oxford)
  comma is the IETF default.
- Use **title case** for the document title and section titles.
- **Use reserved example domains/addresses** (RFC 2606 / BCP 32: `example.com`,
  `example.net`, `.example`; RFC 5737 / RFC 3849 IP ranges) in all examples — never
  real domains or addresses.
- Wrap bare URIs in angle brackets (`<https://example.com/>`).
- Run **idnits** (or the datatracker submission checks) before submitting.

### Writing Change History Entries

Each substantive edit gets a bullet under the current draft revision's `=== Change from … to …` heading (create the heading for the new revision if it does not yet exist).

Keep entries **terse**: state the action and point to the affected section by cross-reference, then stop. Do **not** append a summary of what the section now says or why the change was made — the cross-referenced section is the source of truth for that detail.

- Pattern: `<Verb> <<anchor,format=title>> to/in <<section-anchor,format=title>>.` (e.g. `Added`, `Clarified`, `Removed`, `Restructured`).
- Reference sections with `<<anchor,format=title>>`, not by literal title text, wherever an anchor exists.
- One bullet per logical change. Do not fold rationale, threat descriptions, or normative detail into the bullet.
- Good: `- Clarified handling of multiple `"_domainconnect"` TXT records in <<dns-provider-discovery,format=title>>.`
- Avoid: `- Clarified handling of multiple `"_domainconnect"` TXT records in <<dns-provider-discovery,format=title>>: invalid records are rejected, at least one valid record is processed, and the Service Provider MAY iterate…` (trailing explanation belongs in the section, not the history).

### `update-index.sh`

`./update-index.sh` regenerates the Document Index by scanning the mmark source for
ATX headings (`#`..`######`, tracking fenced code blocks so `#` inside JSON isn't
mistaken for a heading) and rewrites the table between the
`<!-- BEGIN AUTO-INDEX -->` and `<!-- END AUTO-INDEX -->` markers. Columns are
`Level | Title | Anchor | Lines`. It auto-detects the source as the last
`src/draft-*.md`; pass a path to override. The script already exists at the repo
root and is tailored to this draft — do not rewrite it.

## Change History

The draft maintains a `# Change History` section with one subsection per revision
("Version 01 to 02", "Version 00 to 01"). Add an entry there whenever you make a
substantive edit, summarising what changed. This is standard IETF practice and
helps reviewers track revisions across submissions.
