## Check 4 — Whole-Document Consistency

### Substantive defects

C01–C25 deferred; tracked in GitHub issue #143 with one sub-issue each.

- [>] C01 (deferred, #144) L482 forbids `authInfo` in any JSON request body, but `domainName.create/update` (L2947, L3116), `contact.create/update` (L3334, L3392) contain it and examples L4252, L4410, L4734 send it. Proposed L482: "When an operation requires the client to present authorisation information (e.g. a transfer request), the client MUST convey it using the `RPP-Authorization` HTTP request header as defined in [@!I-D.ietf-rpp-core] and MUST NOT include it in the JSON request body. A server MUST reject such a request when its JSON body contains the `authInfo` data element. This rule does not apply to setting the `authInfo` data element of an object in a create or update request."
- [>] C02 (deferred, #145) L1741 says `authdata` MAY be omitted from read responses, but `authInfo.read` (L1755) requires it → `"required": ["@type", "method"]`. **(wire)**
- [>] C03 (deferred, #146) Approve request body contradicts itself: L2743 "MUST always have a request body, which may be an empty JSON object"; L3231 "Both Approve and Delete (Cancel) operations have no request body"; L4540 "empty JSON object" but example L4545 carries `@type`; open comment L4549. Decide one model and align L2743, L3231–L3233, L4540–L4549.
- [>] C04 (deferred, #147) L1080/L1087 Identifier: RFC 5730 `roidType` is `(\w|_){1,80}-\w{1,8}` (max 89). Prose ("one to eight … one or more") and pattern `^(\\w|_){1,8}-\\w{1,}$` have the quantifiers swapped → pattern `"^(\\w|_){1,80}-\\w{1,8}$"`, prose "one to eighty word characters or underscores, followed by a hyphen and one to eight word characters". All example ids still match. **(wire)**
- [>] C05 (deferred, #148) L222 and 30 `"writeOnly": true` annotations: JSON Schema `writeOnly` means the value is never returned by the server, yet create-only elements (`name`, `id`, `period`, `transferDir`, status `label`/`reason`, `authInfo` fields…) appear in read views. Recommend dropping the `writeOnly` rule and annotations (the `update` view already excludes create-only elements), or stating explicitly that `writeOnly` is used in a non-standard sense. **(wire, scripted)**
- [>] C06 (deferred, #149) DNSSEC contradiction: L1692 "ds and dnskey MUST be supported" then "A server MUST support either ds or dnskey or both"; L1576 also requires both. Proposed L1692: "In the EPP Compatibility Profile with the DNSSEC Extension [@!RFC5910], a server MUST support records of type `ds`, `dnskey`, or both, in addition to `ns`, `a`, and `aaaa`. A server that receives only `dnskey` records MUST calculate the corresponding DS record." and align L1576.
- [>] C07 (deferred, #150) L1973 constrains `type`, but `organisationRole` has no `type` (role type is the key of `roles`) → "Each key of the `roles` data element MUST be a value registered in the IANA "EPP Organization Role Values" registry ([@!RFC8543])."
- [>] C08 (deferred, #151) L3542 "`contacts` keys" — `contacts` is an array of labelled objects, not a dictionary; and RFC 8543 does not appear to create an "EPP Organisation Contact Types" registry. → "Each `label` in `contacts` MUST be a contact type defined in [@!RFC8543]." (please verify the RFC 8543 section / registry).
- [>] C09 (deferred, #152) L3843 "The `"status"` array MUST contain exactly one…" — User `status` is a single object (L3861, L3885) whose `enum` already enforces this → delete the bullet and the now-empty constraints block (L3842–L3843).
- [>] C10 (deferred, #153) L3737 says the create representation carries `id`, `creationDate`, `status`, but `message.create` (and example L5569) contain only `data` → "Create request schema. Only the server is authorised to create Message Data Objects."
